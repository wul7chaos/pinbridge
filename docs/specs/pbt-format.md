# `.pbt` 轨迹格式规范 v1

> **这是一份契约**。Rust（`crates/pinbridge-trace/src/pbt.rs`）与
> Python（`python/src/pb/trace/pbt.py`）是它的两个实现，
> 两者共享同一组**黄金字节**用例（见文末）。
> 任何一侧偏离规范都会被测试同时发现。

## 1. 容器

```text
File  := "PBT1"(4 字节) | version u16 LE | flags u16 LE | Chunk*
Chunk := tag u8 | length u32 LE | payload[length]
```

共 8 字节文件头，其后是 chunk 序列。

### 为什么是 chunk 序列，而不是"一个 section 一个长度"

录制线程必须**边跑边写**。定长 section 头要求在写之前就知道总长度
（要么全缓冲、要么回头 seek）。一条 5 分钟 VMP 会话的轨迹可能几十 GB，
两种都不可接受。chunk 让"边产边写"成为可能；读侧把**同 tag 的 chunk**
视为同一逻辑段的延续。

### 段 tag

| tag | 名称 | 可出现次数 | 负载 |
|-----|------|-----------|------|
| `0x00` | META | 1 | UTF-8 JSON（工具版本、样本哈希、架构、启动参数） |
| `0x01` | EVENT | 0..n | 事件记录流（见 §3） |
| `0x02` | AUDIT | 0..n | UTF-8 JSON Lines（每行一条审计记录） |
| `0x03` | SUMMARY | 1 | UTF-8 JSON（见 §5） |
| `0x7F` | END | 1（最后） | 空 |
| 其它 | — | — | **读侧必须按长度跳过**（向前兼容的唯一实现方式） |

约定：`0x00..=0x3F` 为本格式保留，`0x40..=0x7E` 给实验性扩展。

### 文件头 flags

| 位 | 名称 | 含义 |
|----|------|------|
| 0 | `FLAG_REPEAT_FOLDED` | 录制时启用了重复折叠 |
| 1 | `FLAG_DELTA_ENCODED` | 记录采用 delta 编码（v1 恒为 1） |
| 2 | `FLAG_TRUNCATED` | 会话被异常中断，尾部可能缺失 |
| 3..15 | 保留 | 必须为 0 |

> 一个**不依赖这些位**的完整性判据：文件里是否存在 `SUMMARY` 段。
> 缺失即代表录制被中断（进程被杀、崩溃）。这不是缺陷，而是**证据**——
> 读侧因此能区分"正常结束的轨迹"与"被中断的轨迹"。

## 2. 整数编码

* **varint**：无符号 LEB128，最多 10 字节。超过 10 字节视为**损坏**（报错）。
* **zigzag**：`(value << 1) ^ (value >> 63)`（算术右移），再按 varint 写。
  小负数与小正数一样只占 1 字节——内存地址双向跳变（±0x40 一样常见），
  这是必要的。

读侧必须区分两种情况：

| 情况 | 增量解码 | 普通解码 |
|------|----------|----------|
| 数据不足（还没读到） | 返回"不完整" | 报错"被截断" |
| 超过 10 字节 | **报错**（损坏） | **报错**（损坏） |

把两者混成一个错误，会让任何一次分片读取都变成疑似损坏。

## 3. 事件记录

```text
record :=
    varint   seq_delta      # 与上一条记录的序号差；首条以基准 0 计算
    u8       kind           # 类型判别值（见 §4）
    varint   thread_id      # 原生 tid（不做 delta：跳变频繁且值大）
    zigzag   addr_delta     # 相对上一条记录 address 的差
    u8       argc           # 0..=8
    argc ×   zigzag arg_delta   # args[i] 相对上一条记录 args[i] 的差
```

规则：

* **序号必须严格递增**。写侧遇到 `<=` 上一条即报错
  （两条记录序号相同会在重放时产生歧义——序号是唯一的时间线依据）。
* `argc` = **与上一条记录相比最后一个发生变化的参数下标 + 1**。
  末尾未变化的参数整段省略：
  * 全新记录（上一条为"空"，args 全 0）时，`argc` 就等于最后一个非零项 + 1；
  * 与参考实现里"寄存器没有变化就不需要记录"是同一个思路。
* 读侧维护 `last_sequence` / `last_address` / `last_args`，
  未写出的参数沿用它之前的值。
* `argc > 8` 视为损坏。

## 4. 事件类型判别值

**数值写入文件，不得重排。新增只能追加，并同步更新下表与三处实现。**

| 值 | 名称 | 语义摘要 | `args` 约定 |
|----|------|----------|-------------|
| 0 | `reserved` | 保留值 | **出现在文件里即为非法**（读侧拒绝） |
| 1 | `breakpoint_hit` | 命中断点 | `[0]=断点地址` |
| 2 | `exception` | Windows 异常时机 | `[0]=异常码 [1]=异常地址 [2]=是否需要搜索处理器` |
| 3 | `syscall_enter` | 系统调用进入 | `[0]=调用号 [1..4]=前四个参数` |
| 4 | `syscall_exit` | 系统调用返回 | `[0]=调用号 [1]=返回值` |
| 5 | `pattern_hit` | 指令模板命中 | `[0]=模板 ID` |
| 6 | `mem_write` | 内存写入 | `[0]=目标地址 [1]=长度 [2]=新值（≤8 字节时）` |
| 7 | `mem_read` | 内存读取（默认不订阅） | `[0]=地址 [1]=长度` |
| 8 | `reg_write` | 寄存器改写 | `[0]=寄存器编号 [1]=新值` |
| 9 | `trap_flag` | 目标设置了 TF | `[0]=位宽(16/32/64) [1]=0 置位 / 1 清零` |
| 10 | `state_change` | 执行上下文状态变化 | `[0]=状态短名（ASCII 打包成 u64） [1]=附加` |
| 11 | `script_output` | 脚本产生的输出 | `[0..]=脚本自定义` |
| 12 | `repeat` | **折叠标记**（只出现在文件里） | `[0]=被折叠条数 [1]=原始类型判别值` |

对应关系：C 头文件 `native/include/pinbridge.h` 的 `pb_event_kind`、
Python `pb.trace.event.EventKind`、Rust `EventKind`。

## 5. 折叠标记与展开语义

`repeat` 记录（见 [../design/trace-compression.md](../design/trace-compression.md)）：

| 字段 | 含义 |
|------|------|
| `sequence` | 该重复段**最后一条**事件的序号 |
| `address` / `thread_id` | 取自该重复段 |
| `args[0]` | 被折叠掉的条数（**不含**第一次出现的那条） |
| `args[1]` | 该重复段的原始事件类型判别值 |

展开规则（**必须逐字节可逆**）：

```text
遇到 repeat 标记：
    取上一条非标记事件的载荷（type/thread/address/args）
    依次生成 args[0] 条事件，序号从"上一条序号 + 1"递增到"标记序号"
    标记自身不产生事件
```

严格模式（默认，取证必须用）额外校验：
标记序号 == 上一条序号 + 折叠条数；折叠条数 > 0；轨迹不以标记开头。

## 6. SUMMARY 段

UTF-8 JSON 对象。字段与 Rust `Summary` 一致：

```json
{
  "records": 71,
  "events": 4069,
  "repeat_folded": 3999,
  "dropped": 0,
  "first_sequence": 1,
  "last_sequence": 4069,
  "truncated": false
}
```

| 字段 | 含义 | 什么时候要警惕 |
|------|------|----------------|
| `records` | 落盘记录数（含折叠标记） | 异常小 → 模板可能过宽，把不同行为合并了 |
| `events` | 展开后的事件条数 | 与直觉差距大 → 先确认订阅集 |
| `repeat_folded` | 被折掉的条数 | 折叠率 > 0.999 → 这段几乎全是一个循环 |
| `dropped` | **背压丢弃数** | **非 0 即代表轨迹不完整** |
| `first_sequence` / `last_sequence` | 覆盖范围 | 与你的分析区间不符时先确认 |
| `truncated` | 是否异常中断 | `true` → 尾部信息缺失 |

折叠率 = `repeat_folded / (records + repeat_folded)`。

读侧对 SUMMARY 的策略：**未知字段忽略、缺失字段取默认值**（向前兼容），
但**缺失整个 SUMMARY 段必须被当作"轨迹不完整"上报**，而不是静默通过。

## 8. 版本与变更流程

| 变更 | 是否提升 `FORMAT_VERSION` | 必须同步 |
|------|---------------------------|----------|
| 新增段 tag（读侧可跳过） | 否 | 本文件 + 常量 |
| 新增事件类型判别值（追加） | 否* | 本文件 §4 + Rust + Python + C 头文件 |
| 改变记录字段顺序/含义 | **是** | 上述全部 + 黄金字节 + 迁移说明 |
| 移除 `SUMMARY` 字段 | **是** | 同上 |
| 新增 `SUMMARY` 字段 | 否 | 本文件（读侧忽略未知字段） |

\* 判别值追加在**同版本**里是允许的，但读侧对未知值的处理是**拒绝**
（不猜），因此"用新版本录的轨迹给旧版本读"会明确失败——
这是刻意的：静默跳过未知事件会让分析结论悄悄丢数据。

## 9. 读侧防御清单（每条都有对应测试）

| 攻击/损坏面 | 防御 |
|-------------|------|
| magic 不对 | 拒绝并说明实际字节 |
| 版本不匹配 | 拒绝并给出双方版本 |
| 声称巨大长度的 chunk | 单 chunk 上限 256 MiB |
| 超长 varint | 超过 10 字节判损坏 |
| 未知事件类型 / `argc` 越界 | 拒绝 |
| 序号非严格递增 | 写侧拒绝（读侧靠 delta 语义） |
| 自相矛盾的折叠标记 | 严格模式拒绝 |
| 截断（chunk 头 / 负载 / 记录中途） | 分别给出可定位的错误 |
| 保留值 `kind=0` | 拒绝 |
