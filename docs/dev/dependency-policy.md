# 依赖策略

## 立场

PinBridge 是一个**会注入到别人进程里**的工具。它的依赖面直接等于攻击面，
而且每一次"顺手加个库"都会让"这个行为是哪一层引入的"更难回答。

所以：**默认不加依赖，加了要写理由。**

## 当前依赖（M0）

| 依赖 | 用途 | 替代方案与为什么没选 |
|------|------|---------------------|
| `serde` + `serde_json` | 协议、工具描述、summary、审计 | 手写 JSON 会让协议演进变成手工同步的噩梦 |
| `thiserror` | 错误类型 | 手写 `Display` 是纯噪音；它不引入运行时代价 |
| `sha2` | 脚本溯源哈希 | 自己实现哈希是典型的伪优化（见下） |

Rust 侧就这些。Python 侧运行期**零依赖**。

## 明确禁止的依赖

`deny.toml` 里显式列出：

| 禁止 | 理由 |
|------|------|
| `reqwest` / `ureq` / `openssl-sys` | 一个能下传代码的调试工具是我们不愿制造的东西；不需要网络栈 |
| `tokio` | 不引入第二个运行时。Hub 用 std 线程 + 有界通道已经足够，而且"谁在什么时候持有锁"更容易推理 |

什么时候可以重新讨论：出现**无法用标准库解决的**具体问题，
并且 ADR 里写清代价。不要用"更现代"当理由。

## 加依赖的流程

1. **先证明标准库做不到**。在 PR 描述里写清你试过什么、为什么不行；
2. 检查许可证是否在 `deny.toml` 的 `allow` 列表里（MIT / Apache-2.0 / BSD / ISC / MPL-2.0…）；
3. 检查它自己带了什么依赖（`cargo tree -p <crate>`）——
   一个 30 个子依赖的"小工具"通常不值得；
4. 更新 `[workspace.dependencies]`（禁止在成员 crate 里写死版本，否则会出现
   同一库的多个版本）；
5. 跑 `cargo deny check`；
6. 在 PR 里说明：**它替代了什么、不引入它的代价是什么**。

## 版本管理

* 内部 crate 一律 `path` 依赖，版本号只在 `[workspace.package]` 维护；
* 外部依赖用**宽松版本**（`"1"` 而不是 `"1.0.229"`），锁定交给 `Cargo.lock`；
* `Cargo.lock` **入库**：这是一个带二进制的工具项目，
  保证所有人和 CI 用完全相同的依赖树；
* 升级依赖**必须单独成 PR**（Dependabot 已按此配置分组规则）。
  理由：一次"顺手升级"会让 VMP 对抗场景下的行为变化无法归因——
  是样本变了还是依赖变了？

## 关于哈希：为什么用 `sha2` 而不是自己写

脚本溯源需要跨语言一致的摘要。选项：

| 方案 | 结论 |
|------|------|
| 自己实现 SHA-256（约 60 行） | ❌ 伪优化。省一个依赖换来"手写密码学代码"，而且要在 C 侧也对齐 |
| 用 `sha2`（RustCrypto） | ✅ 生态标准件、有审计、跨语言有对应实现 |
| 用 BLAKE3 | 更快，但 Python 侧需要额外依赖，与"运行期零依赖"冲突 |

**判定标准**：跨语言的哈希必须是**标准算法**，因为两边要独立实现并互验
（我们有 `test_sha256_matches_the_rust_hub_constant` 这条用例）。

## 审计与告警

`.github/workflows/deny.yml` 每周跑一次，即使没人改动代码——
这样上游新发的公告能被发现，而不是等到下一次有人升级依赖。

| 检查 | 行为 |
|------|------|
| 许可证 | 不在白名单 → 失败 |
| 已知漏洞（advisory） | 失败；如需放行必须在 `deny.toml` 写理由与跟踪 issue |
| yanked 版本 | 失败 |
| 依赖来源 | 只允许 crates.io 官方 registry（`unknown-registry = "deny"`） |
| 重复版本 | 警告（`multiple-versions = "warn"`） |

## 前端（apps/desktop）

桌面的依赖面单独放在 `apps/desktop/package.json`，不参与 Rust 的依赖策略。
但同样的规矩适用：**加一个 UI 库要能被这个仓库的维护者长期维护**。

## 什么时候可以"不加依赖但自己写"

允许自己写的场景：**小而稳定、且与项目领域强相关**的东西。

已有的例子：

| 自己写的 | 为什么 |
|----------|--------|
| varint / zigzag（`pinbridge-trace/src/varint.rs`） | 十几行、规范就是我们的、需要逐字节控制 |
| `civil_from_days`（时间格式化） | 20 行、只为输出可读时间戳，不值得引入 `chrono` |
| 极简 JSON 字符串转义（hub 里的 `json_string`） | 只为一个字段服务，不引入额外路径 |
| `_BytesIo`（Python 侧的只读字节流包装） | 避免为一个简单需求引入状态机 |

共同点：**能在一个屏幕内读完、并且有测试覆盖**。
反过来，"半个 HTTP 客户端" "半个加密库" 都不属于这一类。
