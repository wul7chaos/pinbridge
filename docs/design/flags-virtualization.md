# TF 虚拟化：为什么"简单清掉 TF"是错的

## 现象

目标设置 `TF`（Trap Flag，单步标志）之后，处理器会在**下一条指令执行后**
产生单步异常（`EXCEPTION_SINGLE_STEP`）。在 VMP 之类的保护里，这个异常
往往不是目标想要的副作用，而是**它主动设计的陷阱**：壳用它来做
指令级校验、反调试，或者借异常流程进入自己的分发器。

## 为什么在插装框架里会出问题

插装（Pin/DynamoRIO）的工作方式是：把目标代码**解码进自己的代码缓存**，
再执行缓存里的副本。于是：

* 目标执行 `POPF`/`POPFD`/`POPFQ` 把物理 TF 置 1；
* 处理器在**代码缓存中的下一条指令**执行后产生单步异常；
* 异常的地址落在 Pin 的代码缓存里，**不是目标预期的位置**。

后果有两类，都很糟：

1. 目标的 `VEH/SEH` 拿到一个"来自代码缓存地址"的异常，它的判断逻辑失效
   （非常容易被当成"检测到了插装"）；
2. 异常时序被改变，壳的控制流走到了与原生执行不同的分支——
   于是你的分析结论是在一条**现实中不会发生的路径**上得出的。

## 两种"看起来显然"的错误做法

| 做法 | 为什么错 |
|------|----------|
| 让物理 TF 生效 | 异常发生在代码缓存地址，暴露插装；时序错乱 |
| 直接用 `PIN_SetContextReg` 清掉 TF | 目标随后可能读标志位（`PUSHF` 后判断），或者依赖这个异常进入自己的 `VEH/SEH`。清掉 = 把目标的逻辑改坏 |

## 正确做法：在**应用指令边界**虚拟化标志位

关键认识：目标看到的应该是"**用户态标志位**"，而不是物理 EFLAGS。
两者在插装框架里可以解耦。

处理流程（当 `POPF` 从栈中读到 TF=1 时）：

```cpp
// 1. 计算"用户态视角"的标志位：TF 被记录在应用上下文里，但不进物理寄存器
PIN_SetContextReg(context, REG_GFLAGS, EmulateUserPopFlags(current, incoming, width));
// 2. 把栈指针按出栈宽度推进（因为指令的语义是"出栈"）
PIN_SetContextReg(context, REG_STACK_PTR, stack_pointer + width);
// 3. 直接把下一条指令地址设为目标期望的位置，跳过物理单步
PIN_SetContextReg(context, REG_INST_PTR, next_ip);
// 4. 置一个"待处理的虚拟单步"标记，交给我们的异常注入路径
AtomicStore(&state->pending, 1);
// 5. 让处理器从我们改写后的上下文继续
PIN_ExecuteAt(context);
```

配套地：

* 当虚拟 TF 处于"待处理"状态时，在**下一条应用指令之后**由我们主动
  产生一次单步异常（注入到目标的异常处理链里），位置与原生执行一致；
* 目标若用 `PUSHF` 读回标志位，读到的是我们维护的用户态值——它看不出区别；
* 目标若用 `POPF` 清 TF，我们同步清掉虚拟标记，不再注入异常。

这样目标看到的是**语义等价的**标志位与异常时序，而物理 TF 从未进入代码缓存。

## 与事件系统的关系

一次虚拟 TF 处理会产生一条 `trap_flag` 事件（判别值 9）：

| 字段 | 值 |
|------|-----|
| `address` | 设置 TF 的那条指令的地址 |
| `args[0]` | 位宽（16/32/64，来自指令形态） |
| `args[1]` | 0 = 置位，1 = 清零 |

有了这条事件，AI 就能回答"目标在什么时候用什么方式打开了单步陷阱"，
而不是只看到一堆莫名其妙的单步异常。

## 状态机

```text
        目标 POPF(TF=1)
              │
              ▼
   ┌──────────────────┐   下一条应用指令执行完    ┌────────────────┐
   │ VirtualTf.Pending├─────────────────────────▶│ 注入单步异常    │
   └────────┬─────────┘                          └───────┬────────┘
            │ 目标 POPF(TF=0)                           │ 异常已交付
            ▼                                            ▼
   ┌──────────────────┐                          ┌────────────────┐
   │ VirtualTf.Clear  │                          │ VirtualTf.Idle │
   └──────────────────┘                          └────────────────┘
```

**状态机必须是每线程的**：TF 是线程上下文的一部分，两个线程的单步状态
互不干扰。把状态放在全局会导致"线程 A 的 TF 让线程 B 收到异常"这种
最难排查的偶发问题。
