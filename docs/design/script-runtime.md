# 脚本运行时

## 为什么是脚本，而不是"更多工具接口"

传统"调试器 + MCP"方案把能力做成一个个固定函数（读内存、读寄存器、下断点……）。
AI 只能在这些函数的输入输出空间里排列组合。遇到这样的任务就断了：

> 脱壳：先观测外壳行为 → 判断 OEP 大致在哪 → 根据 OEP 处内存属性决定
> Dump 时机 → 再修正属性 → 验证 dump 出的 PE 能不能加载。

这不是"几个函数调用"能表达的，它是**带分支和回退的流程**。
所以 PinBridge 的主要工作方式是：**AI 写一段脚本，注入目标进程执行**。
MCP 工具层刻意保持薄（开门、观察、收尾）。

好处不只是"自由度更高"：

* 判断逻辑在**目标进程内**执行，不需要把上下文一轮轮搬回 LLM；
* 中间的循环/试错不消耗 token；
* 脚本自带状态（可以记住上一次命中的地址），不需要往 LLM 上下文里塞。

## 运行时选择：内嵌 CPython

| 候选 | 取舍 |
|------|------|
| **内嵌 CPython** | ✅ 采用。生态成熟、AI 生成质量最高、调试体验好 |
| JS（Frida 路线） | 生成质量尚可，但二进制处理的库生态弱于 Python |
| Lua | 体积小，但 AI 生成的正确率明显更低 |
| WASM | 隔离性好，但拿不到指针，做不了插装侧的活儿 |

代价必须写清楚：**内嵌 CPython 会把解释器带进目标进程**。
具体影响：

* 目标进程的内存占用增加（几十 MB 量级）；
* `os`/`subprocess`/`ctypes` 这类模块必须被**禁用**（见下文沙箱）；
* 目标可能通过"进程里多了解释器"这类特征做检测（属于对抗范畴）。

## 落地进度与装载方式（实测记录）

### 解释器怎么装进目标进程：**运行时动态加载**，不链接导入库

链接 `python314.lib` 会把 `pinbridge_agent.dll` 变成"依赖 `python314.dll` 才能加载"。
后果很具体：任何没装 Python 3.14 的机器上，**agent 整个加载不了**——连"读内存"
这种跟 Python 完全无关的能力也一起没了，而且报错发生在 `LoadLibrary` 那一层，
离真正的原因很远。

所以实现走的是和桥接层/agent 自身同一套办法：`LoadLibraryA` + `GetProcAddress`，
按 `python3.dll`（稳定 ABI）→ `python314.dll` → … 的顺序试，也支持用
`PINBRIDGE_PYTHON_DLL` 显式指定。收益是**没有 Python 时框架仍然完全可用**，
只有脚本能力明确报"不支持"。

三条已经写进代码并在测试里锁住的约定：

1. **显式指定却加载失败不回退**。回退会让"我指定的库没生效"变成一个沉默的事实。
2. **不接管信号处理**（`Py_InitializeEx(0)`）。目标进程的信号/异常处理是它的，
   我们替它装一套会让目标行为发生它自己都不知道的改变。
3. **不是我们的解释器就不碰**。如果进程里已经有别的代码初始化过解释器
   （例如目标自己嵌了 Python），我们只使用、**绝不 finalize**——那会把目标的
   解释器拆掉，表现为"目标在某个时刻莫名崩了"。

### 已落地 / 未落地（诚实标注）

| 能力 | 状态 | 证据 |
|------|------|------|
| 定位并加载解释器、初始化、执行脚本、收尾 | ✅ | 单测在进程内跑 `assert 6 * 7 == 42`、`sys.version_info[0] == 3`；未捕获异常返回明确错误 |
| 缺 Python 时的可行动报错 | ✅ | 单测：报错带上库名与 `PINBRIDGE_PYTHON_DLL` 提示，且**不回退** |
| **策略检查先于解释器** | ✅ | 导出面测试：策略违规报 `invalid_argument` 且文本里**不出现**"解释器"；干净脚本才走到解释器这一步 |
| `pb.subscribe` / `pb.log` / `pb.mark` | ✅ | 纯 Python 的 `pb` 模块由 agent 注入；导出面测试跑通了加载 → 订阅 → 事件驱动 → 输出成事件 |
| 探针回调分发（事件 → 脚本函数） | ✅ | `pb_push_event` 在入队**之前**分发；事件名用 `EventKind::name()`，与脚本里的写法同一张表 |
| `pb.read` | ✅ | **反向调用**（脚本要求 agent 做事）：Rust 用 `PyCFunction_NewEx` + 一张静态 `PyMethodDef` 给出原生可调用对象。能力闸门在 Rust 侧（脚本改不了），拒绝时抛 `RuntimeError` 且原因与 Hub 侧完全一致 |
| `pb.snapshot` | ✅ | 反向调用：读内存（过同一道能力闸门）→ **分块落盘**到给定路径 → 返回写入字节数；同时写一行审计（地址、长度、路径、校验和）。有 256 MiB 上限，超限**明确拒绝**不截断 |
| `pb.defer` | ✅ | 回调里只排队，宿主在**回调返回之后**执行（见下文） |
| 脚本预算的**强制**中断 | ✅ | 看门狗线程 + `PyThreadState_SetAsyncExc` 异步注入 `_PBTimeout`。超时 → `Status::Timeout`、脚本**不注册**、状态机标记 `TimedOut`、写审计行。见下文「预算强制」 |
| 输出文本进轨迹的审计通道（`.pbt` 的 AUDIT chunk） | ⏳ | 目前文本留在脚本侧输出里，事件里只有**数字**（`.pbt` 的事件模型就是数字） |

### `pb` 模块：为什么用纯 Python 注入，而不是写 C 扩展

C 扩展要自己摆 `PyModuleDef` / `PyMethodDef` 的结构体布局——写错就是**目标进程里的
随机崩溃**，而且现场离原因很远。这一层需要的东西（收集输出、按事件名分发、
把 payload 变成带属性的对象）用 Python 表达更短也更清楚。

Rust 只保留两个窄入口：

| 入口 | 方向 | 约定 |
|------|------|------|
| `_pb_drain_json()` | 脚本 → Rust | 返回 `[[kind, value, text], …]`（并清空脚本侧队列）。`kind`：1 = log、2 = mark、3 = subscribe |
| `_pb_dispatch(combined_json)` | Rust → 脚本 | 传入 `{"event": 名字, "payload": {...}}`，返回**被调用的订阅者数量**（0 表示没人订阅） |

两条已经写进代码并被测试锁住的约定：

1. **订阅列表以脚本的实际调用为准**，不解析源码文本。`pb.subscribe` 可能写在条件
   分支里、名字可能是拼出来的；文本解析会给出一个"看起来对但没生效"的列表，
   而分发侧只看列表——脚本会**静默地**永远收不到事件。
2. **订阅了不认识的事件名要报出来**（`invalid_argument`），不能当没发生过。

事件名与 `EventKind::name()` 用**同一张表**：两处不一致的话，脚本会
"注册成功但永远不被调用"，那是最难查的一类问题。

### 反向调用：脚本怎么让 agent 做事（`pb.read`）

前面的 `pb.log` / `pb.mark` 是**单向**的（脚本产出 → agent 收走，走一个 JSON 队列）。
`pb.read` 不同：脚本要**同步**拿到结果，这就要求宿主给出一个真正的 Python
可调用对象。

做法：Rust 用 `PyCFunction_NewEx` + 一张**静态** `PyMethodDef` 造出可调用对象，
放进 `__main__`，再由引导脚本把它接到 `pb.read` 上。

* 只写 `PyMethodDef`（4 个字段）、**不写 `PyModuleDef`**（字段多一倍）：
  我们只需要一个可调用对象，不需要注册模块。
* 方法表必须是静态的：**CPython 只存指针、不拷贝**，放栈上会变成悬空指针。
* 对外长什么样由 Python 决定（名字、docstring、包装），Rust 只提供最小原生函数。

两条刻意的设计：

1. **能力闸门在 Rust 侧**。脚本能改 Python 里的任何东西，闸门放在够不着的那一侧
   才有意义。`pb.read` 内部直接调用 agent 自己的 `pb_memory_read` 导出——
   于是 Hub 侧与脚本侧**走的是同一个门**，不存在"脚本专用的小门"。
2. **拒绝必须抛异常，不能返回空数据**。返回空数据会让脚本把"没权限"当成
   "这段内存是零"，那是**静默的错误结论**，比报错危险得多。异常文本与 Hub 侧
   完全一致（`能力不足: 需要 MemRead，当前持有 CapabilitySet(0)`）。

## 寄存器：谁负责抓，谁负责存

`pb_registers`（MCP 工具）背后是三段：

```
Pin 工具回调（唯一能拿到探针线程 CONTEXT 的地方）   抓
        ↓ pb_set_thread_registers(thread, values, 8)   跨边界，在冲刷线程上
agent（pb_register_name / pb_read_registers / pb_thread_ids_with_registers）  存与取
        ↓ 链路 ReadRegisters
Hub / MCP `pb_registers`                            问
```

**为什么 agent 不能自己抓**：agent 在目标进程里，但它拿到的"当前线程"永远是
**为请求服务的那条线程**（Link 线程 / 冲刷线程），而不是探针命中的那条。那份寄存器
和用户想看的东西毫无关系，却看起来像合法数据——这是最坏的组合。

三段里已完成两段（agent 存与取 + 链路），**捕获段尚未落地**，原因见下。

### 捕获段：已接通（`IARG_REG_VALUE`），端到端有断言

```
Pin 工具回调（唯一能拿到探针线程寄存器的地方）      抓
        ↓ pb_set_thread_registers(thread, values, 8)   跨边界，在冲刷线程上
agent（pb_register_name / pb_read_registers / pb_thread_ids_with_registers）  存与取
        ↓ 链路 ReadRegisters
Hub / MCP `pb_registers`                             问（MCP 工具接线是下一步）
```

端到端证据（`ctest -R pin_tool_agent_end_to_end`），摘要末尾两段就是它：

```
PB_AGENT_CHECK script_output=22 ssn_mark=1 breakpoint_hit=1 memory=1 registers=1 rip=0x7FF7A5B32580
[pinbridge]   寄存器快照：转发层支持（交付 2700 次，失败 90 次，跳过 620 次无效）
```

`registers=1` 的含义是**严格**的：靶子枚举"有快照的线程"、逐个读回 8 个值，
只有当 `RIP` 落在**它自己主模块的地址范围**里才计数。抓错线程、读到全零、
参数顺序错位（把 RSP 当 RIP）都会让这一格是 0。

实现上的三个决定：

1. **取寄存器用 `IARG_REG_VALUE`，不是 `IARG_CONTEXT` + `PIN_GetContextReg`。**
   后者在这个工具的回调里稳定 `RECEIVED_ACCESS_FAULT`（排除过程见下一节）。
   RIP 用 `IARG_INST_PTR`——`IARG_REG_VALUE` 不支持指令指针寄存器。
2. **入口探针把快照写在文件级的"最近一次快照 + 它属于哪条线程"里**，而不是直接写
   `ThreadStats`：入口探针在文件里靠前，那时 `ThreadStats` 还是**不完整类型**
   （定义在几百行之后），解引用成员会得到 `C2027: 使用了未定义类型`。
3. **交付时要求线程号对得上**（`flush_ring` 里 `g_last_registers_thread == slot.thread_id`）：
   对不上就是别条线程的快照，**张冠李戴比"没有"更糟**。

### 为什么"全零的快照"必须被拦住

agent 侧是"每线程最近一次"的**覆盖式**存储，所以把 8 个零交上去会把同一线程
先前那份**有效**快照冲掉。实测过一次：工具报"交付 3419 次"，agent 里 5 条线程
全有快照，读出来却全是 0 —— 于是"RIP 必须落在主模块内"这条断言失败，
而错误信息里没有任何线索指向"被零覆盖"。

现在交付前判 `RIP != 0`（真实执行流里 RIP 为 0 不可能出现），并且把跳过次数
报出来：**"有快照"与"快照有用"是两件事**，只断言前者会把这种缺陷放过去。

### 三条工程教训（都写进代码注释了）

* **读编译器的第一条错误，不要读尾巴**：一个真实错误（类型未声明）会级联出
  上百条"`stats` 未声明"，而构建脚本当时只显示 `-Last 6` —— 看到的是级联的尾巴，
  真正的错处在上面。这一点耽误了整整一轮，脚本已改成显示 `-First 8`。
* **参数顺序错了不会报错，只会读到错位的寄存器**：插桩点按新顺序传了 9 个参数、
  回调签名还是旧的，"入口点命中 0x…"打出来的是**栈地址**，编译通过、运行不崩。
  只有"断言语义"的用例能抓它。
* **两个 agent 实例**：靶子自己 `LoadLibraryA` 一份、桥接层也加载一份，路径不同时
  Windows 给出两个独立模块（导出面是进程级单例），于是工具侧报"交付 3419 次"、
  靶子这边读到 0 条。修法是两边加载**同一条路径**（`PINBRIDGE_AGENT_DLL`）。


**一、`IARG_REG_VALUE` 是可行的替代（已验证不崩）。** 把入口探针改成
`IARG_INST_PTR` + 七个 `IARG_REG_VALUE`（RIP 用前者——`IARG_REG_VALUE` 不支持
指令指针寄存器），跑起来**不崩**，工具侧报告"交付 3419 次"快照到 agent。
也就是说上一轮那条"改用 `IARG_REG_VALUE`"的判断是对的，路是通的。

**二、参数顺序错了不会报错，只会读到错位的寄存器——而且错误信息会指向别处。**
入口探针那一版插桩点已经改成传 9 个参数（tid + rip + 7 个寄存器），但回调签名
还是旧的 `(tid, ctxt, address)`，于是 `address` 收到的是 `RSP` 的值：
**编译通过、运行不崩、打印出来的"入口点命中 0x..."是一个栈地址** ✗
这类"能跑但含义错了"的缺陷，只有"断言语义"的用例能抓（例如"RIP 必须落在主模块里"）。

**三、（最重要）这条端到端用例原本在同时驱动**两个 agent 实例**。**
靶子自己 `LoadLibraryA` 一份 agent，桥接层也加载一份；路径不同时 Windows 给出
**两个独立的模块**，而 agent 的导出面是**进程级单例**。表现是：工具侧报"交付
3419 次快照"，靶子这边 `registers=0`——因为它在问**另一个实例**。
修法是让两边加载**同一条路径**（环境变量 `PINBRIDGE_AGENT_DLL`，桥接层本来就支持，
只是这条用例没设）：现在 ctest 显式设置了它，于是这条用例测的是**真正的共享管线**。
顺带把靶子的取值循环从"固定 8 批"改成"取到看见自己的事件为止"——共享实例后，
排在自己前面的是几千条探针事件，固定批数只会得到"什么都没取到"这种误导性的失败。

**四、全零的快照不是快照，是"没有"。** 溢出槽（线程槽位用尽后的共享槽）从来没被
写过寄存器，它交上去的是 8 个零；而 agent 侧是"每线程最近一次"**覆盖式**存储，
于是零值会把同一线程先前那份好快照冲掉。工具侧现在只在 `RIP != 0` 时交付，
其余情况计入"跳过无效"——**"有快照"与"快照有用"是两件事**，只断言前者会把这种
缺陷放过去。

**结论**：捕获段目前停在"工具侧能取到寄存器、能交付、不崩"，但**尚未接通到主干**：
最后几次改动没能干净落地（前缀声明缺失导致编译器报的是"`stats` 未声明"而不是
"`stats_for` 未声明"，现场与原因差三行），所以这一轮把工具侧改动整体撤回，
只留下上面四条**可复现的结论**与 ctest 的环境修复。下一轮按这四条结论重做，
应当一次就能接通。
### 本轮实测：`IARG_CONTEXT` + `PIN_GetContextReg` 在本工具的回调里会 fault

按最直观的写法（插桩点加 `IARG_CONTEXT`，回调里 `PIN_GetContextReg(ctxt, REG_*)`）
做了一版，结果是稳定崩溃：

```
E: UPC Dispatcher: Unhandled internal exception in Pin or tool.
   IP: 0x7ffe6561ffdb  Exception Code: RECEIVED_ACCESS_FAULT
   Access Type: READ  Access Address = 0xffffffffffffffff
```

已经排除的可能：

* 不是某个寄存器的问题——只读 `REG_INST_PTR` 一样崩；
* 不是名字空间的问题——`LEVEL_BASE::REG_INST_PTR` 一样崩；
* 不是写入的问题——把结果读进一个**局部变量**再丢弃，一样崩；
* 不是 `IARG_` 顺序不对——入口探针传的是 `IARG_THREAD_ID, IARG_CONTEXT, IARG_INST_PTR`，
  与回调签名 `(tid, ctxt, address)` 对得上。

所以 `PIN_GetContextReg` 在这个工具（`PIN_StartProgram` + 回调内入队）的上下文里
**不可用**，而失败模式是"整个目标进程带着 Pin 一起崩"，不是可降级的错误。

**下一步（M2）**：改用 Pin 官方支持的取寄存器方式——`IARG_REG_VALUE`。
同一个文件里系统调用探针**一直**在用 `IARG_REG_VALUE, LEVEL_BASE::REG_RAX` 读寄存器
（那是被验证过能工作的路径）。代价是每个命中点要写 8 个 `IARG_REG_VALUE`，回调签名
多 8 个参数，所以这是"多写几行"而不是"换个 API"。

**这一轮为什么先停在这里**：一条会把目标进程连 Pin 一起打崩的采集路径不能进主干，
哪怕它"大部分时候能用"。留一个抓不到寄存器的诚实实现（读回来会说"这个线程还没有
快照"），比留一个偶尔把被测进程打崩的实现要好。

### 追加能力不能变成硬依赖

寄存器快照是 M1 的**追加**能力，所以：

* 桥接层把它当**可选符号**解析：旧版 agent DLL 没有它只是拿不到寄存器，
  不该让"旧 agent + 新桥接层"这种完全可用的组合直接起不来；
* Pin 工具侧同样按可选处理（`g_api.set_thread_registers != nullptr` 才交）。

这条曾经被违反过一次：桥接层把它算进"导出面不全"，于是新桥接层配一个稍旧的
agent DLL 直接 `pb_attach` 失败——**错误信息指向"缺符号"，而真正的问题是
"我们要求了一个本来可选的符号"**。

## 暂停 / 继续的语义

**这是"采集"的暂停与继续，不是"目标线程"的暂停与继续。**

`pb_pause()` 停下三件事：写轨迹、放进可被取走的队列、分发给脚本。
`pb_continue()` 恢复它们。目标进程**一直在跑**——我们既不冻它，也不影响它。

为什么不做成"冻结目标"：那需要让目标的所有线程同时停下来，而 Pin 不是调试器，
线程由目标自己调度。半吊子的实现会在多线程目标里表现成随机崩溃或死锁，
而调用方还以为自己拿到了一份一致快照——**这种误解比功能缺失危险得多**。

四条写进代码并被测试锁住的约定：

1. **暂停期间到达的事件仍然被计数**（`pb_stats(3)`），恢复时把条数带在状态变化
   事件里。静默丢弃会让"暂停期间目标到底做了什么"变成无法回答的问题——
   而那正是分析里最容易出错的地方：看起来没问题，其实少了一段。
2. **状态变化事件自己不被跳过**（`push_event` 对 `StateChange` 例外）。
   否则暂停开始的那条事件会被自己的规则吃掉，轨迹里只剩一段空白。
3. **重复调用不报错，但明确说"没有影响"**：调用方的记账错误必须以可观测的
   方式暴露（"我以为暂停了 / 我以为还在跑"这类误解不能靠猜）。
4. **附加（`pb_attach`）重置会话状态**：每次附加都把暂停状态与计数清零。
   把上一次会话的状态带过来会表现为"我刚附加上却收不到事件"——
   实测过一次，那条失败信息里没有任何线索指向暂停。

## 单步：为什么不做调试器语义

调试器的"单步"依赖一个前提：它**控制着目标的执行**——能停下线程、执行一条指令、
再停下。Pin 不是调试器（同上的理由）。

硬做会得到一个"看起来像单步、实际不一致"的东西：目标的其他线程仍在跑，
调用方拿到的不是一致快照，而它以为是一致快照。

所以 `pb_single_step` **明确不做**，并且：

* **桥接层必须导出它**（`native/src/agent_bridge.cpp`）：否则调用方拿到的是
  "符号缺失"，那是"桥接层坏了"的语义，而我们要表达的是"这个能力还没做"。
* 错误码区分得很清楚：没有 `single_step` 能力 → `CapabilityDenied`；
  有能力但没实现 → `TargetUnavailable`。调用方据此决定"去要权限"还是"换方案"。
* **现在能用的替代**（都是真实实现）：探针侧三层过滤 + `pb_pause`；
  `pb_set_breakpoint`（命中一次自动解除，可重复下）。
* 指令级逐步记录属于 **M2**，届时语义是"记录接下来的 N 条指令"，
  而不是"让目标走一步"。

### `pb.defer`：把重活移出热回调

回调跑在**目标线程**上，必须极快返回：在里面做重活会拖慢目标，而被分析的程序里
那些对时序敏感的代码会因此表现异常——"目标变慢了"与"目标本来就这样"几乎无法区分。
所以规则是：**回调里只做判断与排队**，耗时的整理解析交给 `pb.defer`。

去重后的执行点是"宿主处理完这条事件之后、在下一次给目标放行之前"：

```
回调：pb.defer(pb.mark, "done", ev.args[0])   # 只排队，立刻返回
      pb.mark("in_callback", pb.pending_deferred())   # 看到"排了 1 个还没跑"
宿主：执行队列 → 队列清空 → 输出随本次一起被取走   # [2, 7, "done"]
```

**边界要说清楚**：deferred 的活**仍然在这条线程上、仍然算在这段预算里**。
"移出回调"移的是"目标此刻不在我们的插装点里"，不是"移到别的线程"。
真正重的活应当**分片**（每次做一小块），否则一段超预算的 deferred 一样会被中断。

一个坏掉的 deferred **不会带走整批**：异常被记下来、剩下的继续跑；
这些异常会进**审计通道**（`script_defer_errors: ...`）——因为 deferred 出错
不会让任何调用失败（那时回调早就返回了），只打日志在"目标跑完就退出"的
常规场景里根本没人看见，脚本会安静地少做一半事。

### `pb.snapshot`：把内存落盘

```
written = pb.snapshot(address, length, path)
```

* 读内存走的是**与 Hub 侧同一道能力闸门**（`MemRead`），没有能力就抛异常；
* **分块**读、分块写，边写边算校验和：8 MiB 一块，避免一次性占用大块内存；
* 失败时说明**从哪个偏移起读不到**——AI 需要知道"边界在哪"，否则只能
  猜是整段不可读还是只有尾巴；
* 上限 256 MiB，超限**明确拒绝**（不截断）："我要 1 GiB，你给我 64 MiB
  且没告诉我"会让上层把半截数据当完整数据用；
* 校验和是 **FNV-1a 64**，**不是密码学哈希**：它挡的是"落盘/传输明显出错"
  与"两次快照是不是同一段"，不挡可构造的碰撞。对抗性完整性要真正的哈希，
  届时单独引入依赖并说明。

一次快照会写一行审计：

```
snapshot: 0x7ff6...1a20 +4096 → C:\dumps\oep.bin（4096 字节，校验和 0x9f3c...）
```

### 事件序号：框架自己产生的事件也要走分配器

有一条不变量容易被忽视：**轨迹记录侧的折叠器要求事件序号严格递增**。
这条不变量被打破过两次，两次的现场都离原因很远（一个 debug_assert 在
测试套件里偶然 panic）：

1. 框架自己产生的事件（`script_output`）**忘了分配序号**，推的是 0；
2. 派生事件（脚本输出、断点命中）**先于**触发它的那条事件入队——
   它们的序号是新分配的，必然更大，于是记录里出现"序号回退"。

现在的规则：

* **框架产生的事件一律走 `pb_allocate_sequence`**；
* `pb_push_event` 里**先入队触发事件，再入队派生事件**——这同时满足
  "因果顺序"（输出紧跟触发它的事件）与"序号单调"两条约束；
* `pb_drain_events` **取完之后**才落断点命中（代价是命中最快在下一次取事件时
  出现；调用方本来就会反复取，这个延迟可以接受，序号单调不可以妥协）；
* **序号 0 视为"没填"**，由 agent 分配一个。0 不是合法序号，把它当"未设置"
  而不是原样入队，是为了不把"调用方随手传 0"变成一个记录侧的隐雷。

#### 预算强制：为什么不用 `sys.settrace`

最直觉的做法是 `sys.settrace` + 一个检查截止时间的跟踪函数（"行级看门狗"）。
**试过，放弃了**，两条都是实测得到的：

1. **超时中断过一次之后，解释器的线程跟踪状态会留下痕迹**，之后再次
   `sys.settrace` 可能**收不到行事件**。表现是：两条预算用例单独跑都通过
   （0.17 s 内正常中断），**一起跑就挂死**——第二次的看门狗静默失效，
   脚本继续死循环。看门狗静默失效比没有看门狗更糟：它让"设置了预算"变成一句空话。
2. **关掉看门狗这一步本身也会被跟踪**：清理调用一执行就被判超时，
   于是"清理"和"看门狗生效"互相打架，永远清不掉。

现在的做法：宿主起一个**常驻看门狗线程**（不是每次调用起一个——回调是热路径，
起线程的开销比脚本还大），到点用 `PyThreadState_SetAsyncExc` 把 `_PBTimeout`
**异步注入**目标线程。它不依赖任何解释器跟踪状态，也就没有上述两个问题。

配套的三件事：

* **超时判定不依赖 Python 侧状态**：看门狗自己记"我这次开过枪没有"，
  宿主撤预算时读这个标志 → `TimedOut`。这样"判定"和"清理"不会互相影响。
* **代号对账**：每次装预算递增一个代号并记下目标线程与截止时间；
  撤预算时只在代号一致时清目标——避免一次已经结束的调用的预算算到下一次头上。
* **注入要检查返回值**：`PyThreadState_SetAsyncExc` 返回 0 表示"解释器里已经没有
  那个线程"，这时超时是**没生效**的，必须说出来，而不是当成成功。

**已知边界（写清楚，不装作没有）**：异步注入只能打断**纯 Python 字节码**的循环。
脚本卡在**阻塞式 C 调用**里（例如对一个超大输入做正则匹配、或者等待 I/O）时打断不了。
这类脚本要靠 `defer`（把重活移出回调）或换算法解决，不是靠调大预算。

#### 脚本换版本与卸载：处理器必须能被收回

`pb.subscribe` 只追加。于是有一个很容易忽视、但后果具体的问题：
**换脚本或卸载之后，旧处理器仍然会被调用**——表现为"我明明改了脚本，
行为却还是旧的"，没有任何错误信息，只有不对的结果。

所以订阅时会**把处理器与当前脚本标记绑在一起**（宿主在执行脚本前设标记），
于是"同名脚本重新加载"和"卸载脚本"都能**只清掉那一个脚本**留下的处理器，
而不是把别的脚本的订阅一起清掉（多个脚本共存是支持的）。

卸载走链路的 `UnloadScript`（从 `not_supported` 变成真实实现）：
状态机迁移到 `Unloaded` + 清掉处理器；清理失败会**明说**（而不是让"处理器还在"
变成一个没人知道的事实）。这与断点必须能被"清"是同一个道理：
只给"下"不给"收"的接口会让使用者在换策略时只能重启会话。

### 审计：判定要留痕

策略拒绝与脚本超时都会往轨迹的**审计通道**（`.pbt` 的 AUDIT 块）写一行，
并且立刻 flush——因为"进程随后可能崩/被杀"正是这些判定最需要被留下的场景，
留在缓冲区里等于没有。

记的是**判定**（我们做了什么决定），不是观测：

```
script_policy_denied: demo 第 1 行命中 os（可以执行外部命令、读写任意文件）
script_timeout: 分发 syscall_enter 超出预算 5000 ms（实测 5019 ms），订阅者 [3] 全部标记为 timed_out
```

超时那行最后半句是刻意的：Python 侧只按事件名分发，我们**无法确定是哪个订阅者
循环了**。与其猜一个，不如如实说清，并把该事件的全部订阅者标记为 `timed_out`
——保守的一侧是"先别再把事件喂给它们"，因为再喂一次只会再超时一次。

#### 加锁顺序：为什么回调要用第二份函数表

分发的加锁顺序是"先锁宿主 → 再取 GIL"，而回调是在**已经持有 GIL** 时被调用的。
如果回调去抢同一个互斥锁，两条路径的加锁顺序就相反了：A 持有 GIL 等锁、
B 持有锁等 GIL——经典死锁。所以回调路径用一份**独立的、只读的**函数表
（加载时再 `LoadLibraryA` 一次同一份 DLL 拿到独立引用），不经过互斥锁。

### 分发顺序：先分发，再入队

`pb_push_event` 里脚本分发发生在事件入队**之前**。这样脚本在回调里
`pb.mark` / `pb.log` 产生的输出，会紧跟着"触发它的那条事件"出现在事件流里；
反过来做，因果顺序在轨迹里看起来是反的。

脚本抛异常**不会让探针失败**：错误记录进 `last_error`，`pb_push_event` 照常成功。
理由是这两件事的因果无关——一个写错的脚本不该把插装链路带崩。

顺序是刻意的：**先验证"解释器能不能在目标进程里活着"**——它是后面所有脚本能力的
前提，也是最容易在别人机器上失败的一环。缺它的时候，其它脚本能力做了也验证不了。

## 脚本形态

```python
# 目标进程内运行，由 PinBridge 提供的 `pb` 模块提供接口
import pb

def on_syscall(ev):
    # ev.args[0] 是系统调用号；这里只在改内存属性时记一笔
    if ev.args[0] == 0x50 and ev.args[1] & 0x20:
        pb.log("potential oep at 0x%x" % ev.address)
        pb.mark("oep_candidate", ev.address)

def on_mem_write(ev):
    if ev.address >= 0x7FF6_0000_3000:
        pb.snapshot(ev.address, 0x1000)   # 记录一段内存到轨迹

pb.subscribe("syscall_enter", on_syscall)
pb.subscribe("mem_write", on_mem_write)
```

接口分三组（M1 落地）：

| 组 | 接口 | 说明 |
|----|------|------|
| 订阅 | `subscribe(kind, callback)` | 声明关心的时机；**订阅集决定开销** |
| 输出 | `log(msg)` / `mark(tag, value)` | 写入 `script_output` 事件（会进轨迹） |
| 采集 | `snapshot(addr, len)` / `read(addr, len)` / `dump(path)` | 需要对应能力 |

## 生命周期

```text
Load ──▶ Active ──▶ Superseded ──▶ Unloaded
           │                │
           └──▶ TimedOut ◀──┘（超时或异常）
```

* **同名重载**：旧版标记为 `Superseded`，**不立即卸载**。
  它可能还有在途回调，强行清掉会在目标进程里留下不一致的中间状态。
* **超时**：默认 `SCRIPT_TIME_BUDGET_MS = 5000`。超时后脚本被标记 `TimedOut`
  并强制卸载——脚本里的死循环会直接冻结目标，这是安全阀不是性能优化。
* **脚本哈希**：每次加载都算 sha256 并写进溯源。回答"当前跑的是哪一版"时，
  哈希比"文件名 + 时间"可靠得多。

## 沙箱：必须禁掉的东西

脚本是**AI 生成的**，它可能出于好意写出危险代码（例如 `os.system("rm -rf")`），
也可能在探索时意外触达。因此 `pb` 运行时的策略是**默认拒绝**：

| 禁止 | 理由 |
|------|------|
| `os` / `subprocess` / `shutil` | 目标进程内的外部命令执行没有任何合法用途 |
| `ctypes` / `cffi` | 绕过我们所有的能力校验直接调系统 API |
| `socket` / `urllib` / `http` | 下传数据与回连；本项目的立场是不引入网络栈 |
| `import` 任意模块 | 只允许白名单（`pb`、`math`、`struct`、`json`、`re`、`binascii`…） |
| `open()` 写模式 | 只有 `pb.snapshot`/`pb.dump` 能在受控路径下写文件 |

**明确说清限制**：这是一个**策略性沙箱**，不是安全边界。
内嵌解释器里做"真正的沙箱"在已知的攻击面前不成立。
它的目的是**防意外**（AI 写出危险代码、探索时误触），
不是防一个已经拿到目标进程控制权的攻击者——那种情况下对方本来就已经赢了。

## 事件分发模型

```text
探针命中
   │
   ├─▶ 构造 Event（序号由 pb_allocate_sequence 分配）
   ├─▶ 折叠器 → .pbt（若在录制）
   ├─▶ 有界通道（满了按 DropOldest 丢弃并计数）
   └─▶ 脚本调度：按订阅集匹配 → 回调
                       │
                       └─ 回调在**目标线程**上执行 ⇒ 必须极快返回
```

**最重要的一条纪律**：回调跑在目标线程上，长时间占用会让目标卡住。
所以：

* 回调里只做"判断 + 记一笔"，重活（扫描、dump、解密）放到下一次 `pause` 之后；
* 我们提供 `pb.defer(fn)` 把工作排到安全的执行点（M1）；
* 单次回调超过预算会被记 `script_output` 警告，并在 summary 里体现。
