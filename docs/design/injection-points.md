# 四类介入时机

PinBridge 把"我们能在什么地方插手"归纳成四类。对 AI 来说这些分类有一部分是冗余的
（它只关心"我要的数据在不在"），但**对人类复核至关重要**：
看到 `syscall_enter` 事件时，人立刻知道自己在看哪一层的观察结果。

分类同时决定了**成本模型**——不同时机的开销差好几个数量级，
subscibe 错了会让目标卡死或者什么都抓不到。

## 总览

| 时机 | 事件类型 | 粒度 | 相对开销 | 默认订阅 |
|------|----------|------|----------|----------|
| 断点时机 | `breakpoint_hit` | 命中点 | 低 | ✅ |
| Windows 异常时机 | `exception` / `trap_flag` | 异常一次 | 低 | ✅ |
| 系统调用 Hook | `syscall_enter` / `syscall_exit` | 一次调用 | 中 | ✅ |
| 指令模板匹配 | `pattern_hit` | 模板首次/每次命中 | **高** | ✅ |
| （附加）内存写入 | `mem_write` | 一次写 | 中 | ✅ |
| （附加）内存读取 | `mem_read` | 一次读 | **很高** | ❌ |

> `mem_read` 默认不订阅：一次成功的 `memcpy` 就能产生几十万条读事件，
> 会把真正有用的信号淹掉。需要它时必须显式订阅，并且接受目标变慢的事实。

## 1. 断点时机

**做法**：插装层在目标地址上放"探针"（不是写 `0xCC`——那是调试器的做法，
会改目标内存、会被 CRC 自校验发现）。命中时构造 `Event` 并入队。

**适用于**：已经知道关注点在哪（OEP、关键分支、校验函数入口）。

**注意**：

* 断点地址是**目标进程虚拟地址**，不是文件偏移。模块重定位后要用运行时基址换算；
* 断点只在"执行到这里"时触发。如果目标从未执行到那里，你什么都看不到——
  这时候应该换用系统调用 Hook 先搞清楚它到底在干什么。

## 2. Windows 异常时机

**做法**：接管异常分发路径，把异常当作观察点（而不是像调试器那样当成
"必须由我处理的事件"）。

**适用于**：目标自己用异常做控制流（常见于壳）、`VEH/SEH` 参与的流程、
以及 TF 单步陷阱（见 [flags-virtualization.md](flags-virtualization.md)）。

**关键区别**：这条路**不依赖 Windows 调试框架**。目标的
`IsDebuggerPresent` / `NtQueryInformationProcess` 类检测看不到"被调试"，
因为从系统视角我们根本没在调试它。

## 3. 系统调用 Hook

**做法**：在系统调用进入/离开时记录调用号与参数。

**适用于**：**不知道要找什么的时候**。这是脱壳场景的主力：

```text
VirtualProtect(脱壳后改属性) → 出现 RWX 区域 → 那里就是 OEP 候选
NtWriteFile / 自解压后的写盘   → 数据流已经成型
CreateThread                   → 壳的第二个执行流
```

**代价**：所有系统调用都会被看到，噪音大。**过滤必须在事件产生之前做**，
而不是产生之后再筛——后者会让通道背压提前到来（见
[../specs/pbt-format.md](../specs/pbt-format.md) 的 `dropped` 字段）。

## 4. 指令模板匹配

**做法**：按字节模板（例如 `8B ?? ?? ?? ?? 85 C0`）匹配指令序列，
命中时记录。

**适用于**：定位一类**行为模式**而不是具体地址，例如
"读取 `PEB` 的那条指令"、"某类校验循环的入口"。

**代价与陷阱**：

* 需要先解码再匹配，成本随模板数量线性增长；
* 模板要写得**足够特异**，否则会命中几十万次（这就是折叠压缩存在的意义）；
* 命中地址会随编译器优化变化，**不要把模板匹配结果写进硬编码脚本**，
  要么用相对偏移，要么让脚本自己重新定位。

## 事件类型与 `arg` 约定

`Event.args` 是定长 8 项。约定如下（与 `EventKind` 的文档注释一致）：

| 类型 | args[0] | args[1] | args[2] | 说明 |
|------|---------|---------|---------|------|
| `breakpoint_hit` | 断点地址 | — | — | address 字段也是断点地址 |
| `exception` | 异常码 | 异常地址 | 是否需要搜索处理器 | — |
| `syscall_enter` | 调用号 | 参数 1..4 | | |
| `syscall_exit` | 调用号 | 返回值 | — | — |
| `pattern_hit` | 模板 ID | — | — | — |
| `mem_write` | 目标地址 | 长度 | 新值（≤8 字节时） | — |
| `mem_read` | 地址 | 长度 | — | — |
| `reg_write` | 寄存器编号 | 新值 | — | — |
| `state_change` | 状态短名（ASCII 打包） | 附加 | — | 见 `hub.rs` 的 `state_code` |

**改动约定就是改协议**：新增字段前先看 [../specs/pbt-format.md](../specs/pbt-format.md)
的类型表，那里是唯一真相。

## M0 现状

| 能力 | 状态 |
|------|------|
| 事件模型 / 序号分配 / 有界队列 / 折叠 / 落盘 | ✅ 已实现且测试覆盖 |
| 断点、异常、系统调用、模板匹配的**真实探针** | ⏳ M1（需要 Pin 运行时） |
| `mem_read` / `mem_write` 的真实采集 | ⏳ M1 |

M0 期间这些动作在 `pinbridge-agent` 里是**桩**：先校验能力，再返回
`not_supported`。顺序不能反——否则"能力校验是否真的生效"就无法被测试覆盖，
等到 M1 换上真实现时，"第一次真正执行权限链路"会发生在最不适合发现漏洞的时刻。
