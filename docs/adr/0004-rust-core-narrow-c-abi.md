# 0004. Rust 主导 + 极窄 C ABI

- 状态：已采纳
- 日期：2026-10-16
- 相关：[../specs/c-abi.md](../specs/c-abi.md)、[`native/include/pinbridge.h`](../../native/include/pinbridge.h)

## 背景

Pin 的工具是 C++（按 Pin 的约定被 `pin.exe -t <tool>` 加载）。
但 PinBridge 的业务逻辑（会话、权限、脚本生命周期、事件模型、轨迹编解码）
如果也用 C++ 写，会带来几个具体问题：

* 内存安全靠人盯（而这个项目里最危险的地方恰恰是"处理目标进程给的数据"）；
* 与 Hub / CLI / MCP 无法共享类型，协议会退化成手工同步的字符串；
* 依赖管理、测试框架、跨平台构建都要另建一套。

## 决策

**Rust 写业务逻辑，C++ 只保留插装必需的那一层**，两者之间用**极窄的 C ABI**：

```text
pin.exe
  └─ pinbridge.dll（C++：探针、JIT 上下文、TF 虚拟化）
        └─ C ABI ─▶ pinbridge_agentdll.dll（Rust：事件、脚本宿主、录制）
```

"窄"的具体含义（写进 [../specs/c-abi.md](../specs/c-abi.md) 的硬性约束）：

1. 只传**定长整数、指针 + 长度、定长数组、`repr(C)` 结构体**；
2. 不允许 `bool`、不允许变长结构、不允许跨边界存活的对象；
3. 不允许异常/panic 穿过边界（release 下 `panic = "abort"`，且导出入口统一捕获）；
4. 字符串是 UTF-8 + NUL 结尾。

并且把**布局契约钉在编译期**：`native/src/abi_selfcheck.cpp` 里用 `static_assert`
断言 `sizeof(pb_event_raw) == 88`、各字段偏移、能力位与事件判别值。

## 考虑过的替代方案

| 方案 | 为什么没选 |
|------|-----------|
| 全部用 C++ | 丢内存安全；与 Hub 的类型无法共享；测试与依赖管理另起一套 |
| 全部用 Rust（含 Pin tool） | Pin 的 API 是 C++；用 Rust 绑它需要 `bindgen` + 大量 `unsafe`，收益为负 |
| 用 CXX / cxx 桥接（Rust↔C++ 自动绑定） | 引入依赖且生成物不可审计；而我们的边界足够窄，手写 8 个函数更可控 |
| 用共享内存 + 自定义协议替代 ABI | 增加一层同步问题；且目标进程内多一个"解析外部数据"的攻击面 |
| 通过 IPC 让 Pin tool 与 Rust 进程分离 | **目标进程的探针必须同进程**，否则读不到上下文；这条不成立 |

## 后果

**得到**：

* 业务逻辑享受 Rust 的内存安全与工具链；
* 跨语言边界只有 88 字节的结构体与几个整数状态码，**可审计、可断言**；
* Hub / CLI / MCP / agent 共享同一套领域类型（`pinbridge-core`）。

**付出**：

* 需要维护两份必须一致的声明（`.h` 与 `abi.rs`）→ 用"同提交修改 + static_assert + 测试"三重约束；
* 每次跨边界调用都有一次转换成本 → 因此**事件推送走批量 `drain_events`**，
  而不是一条一条调；
* ABI 版本不匹配时必须拒绝加载（不做"尽力兼容"）——
  一个错位的函数指针会把目标进程直接打崩，而崩因会指向目标程序本身。
