# 0001. 用插装框架做基座，不用调试器框架

- 状态：已采纳
- 日期：2026-10-16
- 相关：[../architecture/security-model.md](../architecture/security-model.md)、[../design/injection-points.md](../design/injection-points.md)

## 背景

要分析一个用户态程序（PC 三环），传统做法是：

1. 基于 Windows 调试框架（x64dbg 及其衍生）—— 依赖 `DebugActiveProcess` 与异常机制；
2. 基于内核层反调试/异常接管 —— 需要驱动；
3. 自研模拟执行 —— 需要自己写虚拟机。

在 VMP 类对抗中发现的问题（与参考文章一致）：

* 目标可以**主动检测**调试器（`IsDebuggerPresent`、`NtQueryInformationProcess`、
  `PEB` 标志位、时序检测），并且可以**故意设计陷阱**；
* 调试器自身依赖异常分发，目标的异常洪泛/异常篡改会直接打击这条路径；
* 用内核调试器分析三环程序是"高打低"，重得离谱——
  那要分析内核/虚拟化本身时该怎么办？

## 决策

以**插装框架**（Intel Pin，代表；DynamoRIO 为开源备选）作为基座。

插装框架把目标代码解码进自己的代码缓存执行，因此：

* **不经过被分析进程的异常路径**，目标的调试器检测看不到"被调试"；
* 能做到**指令级**粒度控制（知道停在哪条指令），从而自建调试器语义；
* 天然支持"在运行代码时插入自己的逻辑"，这正是四类介入时机的载体。

## 考虑过的替代方案

| 方案 | 为什么没选 |
|------|-----------|
| Windows 调试框架 | 依赖异常路径，容易被针对；下断点要改目标内存（会被自校验发现） |
| 内核驱动接管异常 | 重；受驱动签名与兼容性拖累；分析三环用内核是"高打低" |
| 自研模拟执行（emoji/Unicorn 类） | 无法翻译的指令与对抗会直接卡死；切内核的指令尤其致命 |
| Frida 类注入 + JS | 分析逻辑与注入都成熟，但 **JS 生态做二进制处理明显弱于 Python**，而 AI 生成 Python 的正确率更高；且 Frida 的 Stalker 在 VMP 指令级场景下开销与可控性不如 Pin 的探针模型 |
| DynamoRIO | 开源、能力接近；**保留为备选**，但当前以 Pin 为准（文档与生态更成熟） |

## 后果

**得到**：

* 指令级观测与控制权，不依赖被分析进程的异常机制；
* 四类介入时机（断点/异常/syscall 钩子/模板匹配）有统一的载体；
* TF 之类的标志位陷阱可以在"应用指令边界"上虚拟化
  （见 [../design/flags-virtualization.md](../design/flags-virtualization.md)）。

**付出**：

* Pin 是**闭源第三方**，按 Intel 自己的许可分发 → 不能入库、需要手工获取；
* Pin 的 API 是 C++，我们必须维护一层窄 C ABI；
* 插装本身有开销（代码缓存、翻译），事件量级远高于原生执行 →
  **这直接引出了 ADR-0005（二进制轨迹格式）与 ADR-0009（有界通道）**；
* 平台受限：Windows/Linux x64 为主，macOS 不可用。

**失效条件**（什么时候该重新考虑）：如果某个目标在插装层就能稳定检测到我们，
并且无法通过 TF 虚拟化/时序缓解，那么"换一个基座"就必须重新评估——
届时请新写一条 ADR，而不是把这条改掉。
