# 0008. 控制权用带 epoch 的租约

- 状态：已采纳
- 日期：2026-10-16
- 相关：[../architecture/control-ownership.md](../architecture/control-ownership.md)

## 背景

本项目的执行者包含 **AI**。它不是"偶尔点一下按钮的人"，而是会：

* 连续下发多条命令；
* 在一次分析里保持一个长任务（装脚本 → 观察 → 改脚本）；
* 在人类介入之后**继续按原计划执行**。

具体危险场景（这是设计这条记录的起点）：

> AI 正在加载一套 hook 脚本。人类中途决定接管，手工改了内存。
> 如果 AI 的在途命令不失效，它下一秒就会覆盖人类刚建立的现场——
> 而**两边都认为自己工作正常**。

这类问题的可怕之处不在于后果，而在于**不可观测**：没有报错、没有异常，
只有一个"过一会儿就变了"的现场。

## 决策

控制权是**带 epoch 的单写者租约**：

```rust
ControlLease { holder: Principal, capabilities: CapabilitySet,
               epoch: u64, expires_at_ms: u64, state }
```

规则：

1. 任何**写操作**都必须携带它签发时的 `epoch`；
2. `epoch` 只在 `renew`/移交时推进（人类 `takeover` 会 `epoch += 1`）；
3. epoch 不匹配 → **拒绝执行**并返回 `ControlConflict`
   （携带当前持有者与两个 epoch），而不是"尽力执行"；
4. 过期是**惰性**判定的（下一次访问时检查），避免在休眠目标里跑心跳线程。

配套的可见性：MCP 层把这个错误翻译成可执行建议
（"请重新 attach 获取新 epoch 后重试"）。

## 考虑过的替代方案

| 方案 | 为什么没选 |
|------|-----------|
| 不加控制权，人人可写 | 人类与 AI 会互相覆盖，且事后无法归因 |
| 用互斥锁（谁持有谁操作） | 锁无法跨进程/跨 MCP 会话表达"意图"；长任务会把锁持有到天荒地老 |
| 用"最后写入者获胜" | 正是我们要避免的静默破坏 |
| 让人类接管时**阻塞**在途命令 | 无法可靠实现（AI 的命令已经在路上）；而且"阻塞多久"没有正确答案 |
| 只在 Hub 侧校验 | Hub 与 agent 之间隔着链路，单点校验会被绕过（见 [../architecture/control-ownership.md §5](../architecture/control-ownership.md)） |
| 用时间戳而非 epoch | 时钟不可靠（目标可能改系统时间），且无法表达"代际"语义 |

## 后果

**得到**：

* "AI 的在途命令失效"这件事变成**可证**的（收到明确的 `ControlConflict`）；
* 冲突从"静默破坏"变成"显式报错 + 可恢复建议"；
* 审计里能对上"这条命令是在第几代控制权下发的"。

**付出与已知边界**：

* 调用方必须维护 epoch（MCP 层为此做了缓存，并且**只有响应带新 epoch 时才刷新**，
  否则 epoch 校验会退化成永远相等）；
* 人类 `takeover` 之后，AI 需要重新 attach 才能继续——这是刻意的摩擦，
  目的是让接管这件事被注意到；
* 租约会过期（默认由 Hub 续租）。如果 Hub 崩了，租约自然失效，
  不会出现"没人能接管"的死锁；
* **epoch 不解决"两个 AI 同时操作"的分配问题**——目前是"先到先得 + 人类裁决"。
  如果需要多 agent 协作，请新写一条 ADR。
