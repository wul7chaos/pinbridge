# 0009. 通道必须有界，丢弃必须计数

- 状态：已采纳
- 日期：2026-10-16
- 相关：[../architecture/security-model.md §威胁 5](../architecture/security-model.md)、[`crates/pinbridge-core/src/channel.rs`](../../crates/pinbridge-core/src/channel.rs)

## 背景

事件产生速率的上限由目标决定，不由我们决定。在 VMP 类目标上：

* 单指令 spin 循环可以每秒产生千万级探针命中；
* 消费端是脚本回调或 Hub——它做的是判断与记录，速度上限远低于产生端；
* **agent 跑在被分析进程内部**：它的内存占用就是目标的内存占用。

于是有一个非常具体的失败模式：

> 目标进入长循环 → 事件堆积 → 队列把目标进程的内存吃光 →
> **分析工具把分析对象搞崩了**。

这比"分析失败"糟糕得多：它会产生一份不完整的轨迹，而且崩溃的原因指向目标程序本身，
排查方向完全错误。

## 决策

所有事件通道**必须有界**，并且：

1. 满时按**显式策略**处理：

   | 策略 | 适用 |
   |------|------|
   | `DropOldest` | 交互式分析（"现在发生了什么"最重要） |
   | `DropNewest` | 录轨迹（保证前缀完整） |
   | `Reject` | 取证模式（宁可断链也不丢证据，写入方显式失败） |

2. **丢弃条数必须被计数，并出现在用户能看到的地方**：
   `Summary.dropped`、`pb_events_query` 的响应字段、`pb_stats`。

3. 三个载体各自上报自己的丢弃量：

   | 载体 | 容量 | 丢弃字段 |
   |------|------|----------|
   | 事件通道 | 固定条数 | `channel_dropped` |
   | Hub 记录窗口 | 固定条数 | `window_dropped` |
   | `.pbt` 文件 | 磁盘 | 不可能丢（写了就是写了） |

4. `clippy.toml` 把 `std::sync::mpsc::Sender`/`SyncSender` 列为**禁止类型**，
   强制所有人走 `pinbridge_core::channel::bounded`。

## 考虑过的替代方案

| 方案 | 为什么没选 |
|------|-----------|
| 无界队列 | 上面的失败模式；等于把"目标会不会被搞崩"交给目标的行为决定 |
| 有界但静默丢弃 | 最危险的一档：AI 会把"我看到的"当成"发生过的"，结论看起来完整但实际错误 |
| 背压（阻塞产生端） | 产生端在目标线程上——阻塞它就是**冻结目标**，直接把分析对象卡死 |
| 溢写到磁盘 | 磁盘 I/O 在被分析进程里不可控（可能触发杀软、可能极慢）；而且磁盘也会满 |
| 只保留计数，不暴露给 AI | 人会看日志，AI 不会。必须出现在 tool_result 里 |
| 用无锁环形缓冲 | 语义上更好，但要自己实现（引入 `unsafe`）；当前有界队列 + 短锁已经足够，且更容易审计 |

## 后果

**得到**：

* **目标不会被我们搞崩**（内存占用有硬上限）；
* 丢失是**可见、可归因**的：`dropped > 0` 时任何结论都必须附带"轨迹不完整"；
* 交互式分析与录轨迹可以用不同策略，各自优化自己关心的那一端。

**付出**：

* 消费端必须处理"丢过事件"的现实（分析脚本要有这个意识）；
* 录制模式选 `DropNewest` 时，尾部会缺——但**前缀完整**，
  这比"前缀缺一块"更容易推理；
* 需要一个明确的容量默认值（当前 65536 条），在"抗突发"与"内存占用"之间取平衡；
* 通道锁在热路径上被持有 → 锁内不允许分配大块内存或做 I/O
  （这条写进了 [../dev/coding-standards-rust.md](../dev/coding-standards-rust.md)）。

## 一条推论：`dropped` 不是错误，是前提

工具不会因为 `dropped > 0` 就报错——那样会让"弱一点的目标"变得无法分析。
它做的是**把前提大声说出来**：

```text
next=2401 dropped=318
注意：dropped 非零，说明有事件因背压被丢弃；结论必须考虑这一前提。
```

这比"失败"或者"假装完整"都更符合分析工作的实际需要。
