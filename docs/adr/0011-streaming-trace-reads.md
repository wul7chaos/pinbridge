# ADR 0011：轨迹的实时流式回传（`.pbt` 的可读边界）

- 状态：已接受（M2「轨迹实时流式回传」）
- 影响面：`crates/pinbridge-trace/src/pbt.rs`（格式语义与读端）、
  `crates/pinbridge-agent/src/host.rs`（冲刷节奏）、Hub 的读端调用方式

## 背景

现状是「录完再读」：`.pbt` 只在收尾时写 `SUMMARY` 与 `END`，读端（`PbtReader`）
遇到半个 chunk 直接报「轨迹在 chunk 负载中途结束」。

于是分析一条**正在录制**的轨迹只有一个办法：等 `finish`。对一次跑几分钟、
产生几十万条事件的目标，"边跑边看"就做不到 —— 而 AI 分析脚本最有价值的时候
恰恰是**目标还在跑**的时候（看到可疑写入立刻决定下一步探哪里，而不是等跑完再回头）。

真正的难点不是"能不能读到字节"，而是**读到的东西算不算数**：

| 风险 | 后果 |
|------|------|
| 读到半个 chunk | 报错就无法流式；不报错就丢字节，之后**全体错位** |
| 读到"还在写的记录" | 拿到一条看似正常、其实不完整的数据 |
| 不知道"完整到哪" | 无法区分"目标还没跑到"与"数据没落盘"，结论会建立在缺数据上 |
| 折叠（`Repeat`）未落盘 | 尾部看起来正常，实际少了一整段被折叠的事件 |

## 决定

### 1. 提交标记：`flush()` 在事件块**之后**写一个 `SUMMARY`

语义：**"在这个位置之前记录是完整的；截至 `last_sequence` 已落盘"**。

- **顺序不可反**：先事件、后标记。反过来会让读者把标记之后、尚未落盘的记录
  当成已完整 —— 这是流式读取最危险的一类错，因为读到的数据**看起来完全正常**。
- 一份轨迹因此会有**多个** `SUMMARY`。读端规则：**最后一个胜出**
  （`finish` 写的那个是权威的）。
  实现上必须**清空再写**，不能 `push_str` 拼接 —— 拼出来是 `{...}{...}`，
  JSON 解析会失败，而失败位置离真正原因很远。（这一处是本次改动**顺带修掉的
  既有缺陷**：此前 `SUMMARY` 只会出现一次，拼接从未被触发。）

### 2. 读端两种模式，判定必须**不同**

| 模式 | 半个 chunk | 理由 |
|------|-----------|------|
| `PbtReader::open`（严格） | **报错**（损坏） | 一份写完的轨迹不该是这样；容忍它会把真正的文件损坏静默成"还没写完" |
| `PbtReader::open_streaming`（流式） | **正常**，停在最后一个完整位置 | 边录边读时这是**预期**状态 |

流式模式下 `next_record() == Ok(None)` 的含义是「**当前**没有更多完整记录」，
**不代表结束**；写入方继续写之后再调用一次就能读到新的。

### 3. 一个字节都不能丢：未读完的零头缓存在读端

底层是"一次性"读句柄，已消费的字节拿不回来。所以读到半个 chunk 时，
已读到的字节（含 chunk 头）原样存进 `pending`，下次调用**先消费它再读底层**。

为什么这条不能省：丢掉半个 chunk 的头，之后所有字节都会错位，
而错位后解析出的"记录"**仍然有 kind、有地址、看起来像记录** ——
这是这类实现里最难发现的一类错误。用例专门验证这一点：
读到截断处 → 补上剩余字节 → **同一个读端实例**必须接着解析出正确的标记。

### 4. 读端要能说出「完整到哪里」

`reader.summary()` 返回**最后一个完整**的提交标记；其 `last_sequence`
就是安全边界。写到一半的标记**不采信**（它覆盖到哪里还不知道）。

### 5. 与折叠的关系

被折叠的事件在 `finish` 前不一定落盘，所以：

> **边界以内的事件是完整的；边界之后可能还有（也可能被折叠掉了）。**
> 流式读到的"最后一小段"不能用来下"这段窗口里没有事件"的结论。

## 代价（如实记账）

- **体积**：提交标记与数据冲刷同频（agent 侧 `FLUSH_EVERY_RECORDS = 64`），
  标记约 150 字节 ⇒ 约 **+2~4 字节/条（≈10%）**。
  想省就要把"标记节奏"与"数据冲刷节奏"解耦（例如每 16 次冲刷写一个标记），
  代价是流式读的边界最多滞后 1024 条 —— 目前没做，因为 10% 换"边跑边看"
  是划算的，而解耦会引入两个节奏参数、要单独写用例。
- **写放大**：每次冲刷多一个小 chunk（一次 `write`）。相对记录量可忽略。
- **滞后**：流式读的可见性最多滞后一个冲刷周期（64 条）。

## 备选方案（以及为什么不选）

| 方案 | 为什么没选 |
|------|-----------|
| 定期把文件**复制/快照**给读者 | 拷贝整份轨迹的开销随轨迹增长，且快照瞬间仍可能落在 chunk 中途 —— 问题只是被推迟 |
| 用原子追加（单一 `write` 系统调用）保证 chunk 完整 | 无法保证：文件系统不提供"多段写入原子"；而且记录本身也会跨多次 `write` |
| 只靠"文件大小"判断完整到哪 | 大小对齐到 chunk 边界不等于内容完整；而且读端无法知道最后一条完整记录的序号 |
| 让读者容忍任何截断（去掉严格模式） | 会把**真正的损坏**静默成"还没写完"，比报错危险 |
| 改成"每次记录后 fsync" | 性能不可接受（每事件一次系统调用） |

## 后果

- 正向：AI 脚本可以在目标运行期间读轨迹前缀，并**明确知道**自己读到哪；
  Hub 不需要等 `finish` 就能展示事件流。
- 负向：文件大 10%；读端多一个模式，"用哪个模式"要在调用点判断清楚。
- 需要遵守的约定：**任何写 `SUMMARY` 的地方都要在事件块之后**；
  读端**不允许**拼接多个 `SUMMARY`。

## 验证

`crates/pinbridge-trace/src/pbt.rs` 的两条用例：

1. `a_reader_sees_a_complete_prefix_while_the_writer_is_still_writing`
   —— 边录边读：提交标记的 `last_sequence` 正好等于已落盘条数；
   写入方继续写之后，**同一读端实例**读到新增记录且**序号接得上**；
   多个标记时最后一个胜出。
2. `a_streaming_reader_tolerates_a_truncated_tail_and_loses_no_bytes`
   —— 同一个截断字节流：流式模式不报错、读到 4 条完整记录、
   且**不采信**写到一半的标记；严格模式**必须报损坏**；
   补上剩余字节后，同一读端实例解析出正确的边界。
