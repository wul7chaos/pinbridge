# 0002. AI 写脚本，MCP 只做薄层

- 状态：已采纳
- 日期：2026-10-16
- 相关：[../specs/mcp-tools.md](../specs/mcp-tools.md)、[../design/script-runtime.md](../design/script-runtime.md)

## 背景

"调试器 + MCP 插件"是当前最常见的 AI 辅助方案：把调试能力包装成一批
MCP 工具（读内存、读寄存器、下断点、单步……），让 AI 调用。

在实践中暴露的问题：

1. **表达能力不足**：函数接口只能控制"已有接口的输入输出"。
   脱壳那种"先观测外壳 → 判断 OEP → 决定 Dump 时机 → 修属性 → 验证"
   是带分支和回退的流程，硬做就要付出更多 token 与来回返工；
2. **主导权在人手里**：插件形态下 AI 是外挂，无法规划跨多轮的分析策略；
3. **上下文不透明**：AI 调用接口之后具体发生了什么、跑了哪个脚本，
   只能靠日志与 debug 溯源；
4. **上下文成本**：把目标进程的中间状态一轮轮搬进 LLM 上下文，既慢又贵。

## 决策

**MCP 工具层保持薄**：只提供三类动作——

| 类别 | 工具 |
|------|------|
| 开门 | `pb_session_list` / `pb_session_create` / `pb_session_attach` |
| 观察 | `pb_events_query` / `pb_memory_read` / `pb_provenance` |
| 投放与收尾 | `pb_script_load` / `pb_trace_record` / `pb_control` / `pb_breakpoint_set` / `pb_capability_grant` |

真正的分析逻辑由 AI **写 Python 脚本注入目标进程执行**：

* 判断、循环、试错、回退都在目标进程内完成；
* 中间状态留在脚本里，不消耗 LLM 上下文；
* 脚本源码的 sha256 进溯源，"当前跑的是哪一版"可回答。

## 考虑过的替代方案

| 方案 | 为什么没选 |
|------|-----------|
| 纯工具菜单（大量细粒度工具） | 表达不了组合流程；token 成本高；探索空间被工具集限死 |
| 让 AI 直接生成汇编/patch 并执行 | 太危险且不可回退；失败代价是"目标崩了" |
| 用 MCP 的 `resources` 暴露"可执行脚本" | 语义不符（资源是读的，不是执行的）；且失去权限校验的落点 |
| 把脚本跑在 Hub 侧（不在目标进程内） | 拿不到目标的地址空间与执行上下文；通信开销爆炸 |

## 后果

**得到**：

* AI 的表达能力从"函数组合"提升到"任意程序"，能处理带试错的流程；
* token 消耗与目标状态的复杂度解耦；
* 脚本自带状态，跨多轮的分析策略变得可行。

**付出**：

* 必须维护一个**内嵌脚本运行时**（CPython），并处理沙箱、超时、生命周期；
* 必须禁止危险模块（`os`/`ctypes`/`socket`…），并明确说明这是**策略性沙箱**
  而不是安全边界；
* 脚本跑在目标线程上 → 回调必须极快返回，重活要 defer；
* MCP 侧的能力校验必须**双端**（Hub + agent），因为"能装脚本"是能力上限。

**关键约束（写在代码里）**：`pb_script_load` 是唯一
`executes_in_target = true` 的工具，且它的权限要求是最强的一档
（`script_load`）。任何新增的"在目标内执行代码"的工具都必须显式登记，
并有测试断言这个清单只有一项。
