# ADR 0012：调用图重建 —— 只画三个信号都齐的边

- 状态：已接受（M3「调用图重建」）
- 影响面：`native/src/pinbridge_tool.cpp`（转移探针）、
  `crates/pinbridge-trace/src/callgraph.rs`（建图）、`docs/design/injection-points.md`（args 约定）

## 背景

需求是「从 `reg_write` + 栈事件还原主要调用关系」。动手前先核对了现实，
结果和计划不一致，记下来：

1. **`reg_write`（kind 8）协议里有，但全仓没有任何产出方**。它在枚举、名字映射、
   ABI 自检里都存在，工具侧却从不发它。所以"从 reg_write 建图"这件事的前半段
   （数据来源）是**缺的**，不是"分析还没写"。
2. 光有 `mem_write`（栈上写的返回地址）**不足以**判定一次调用：跳转、异常展开、
   手工改栈都会产生"往栈上写一个代码地址"的形状。
3. 反过来，`INS_IsCall` / `INS_IsRet` 在 Pin 里是**精确**的指令分类 ——
   比事后从内存写入猜要可靠得多。

## 决定

### 1. 数据来源：工具侧新增「转移探针」（`-pb_transfers`）

只对**调用与返回**插装（不碰普通分支：收益低、点位多、噪声大）：

| 指令类别 | `args[2]`（转移码） |
|----------|--------------------|
| `INS_IsCall` | `1` |
| `INS_IsRet` | `2` |

事件形状沿用既有的 `RegWrite`（kind 8），不新增 kind —— **格式不变**：

```
args[0] = 寄存器编号（0 = rip，见 pinbridge_trace::REGISTER_NAMES）
args[1] = 转移目标地址
args[2] = 转移码（1=call 2=ret；0/缺省 = 未知，**不用于建图**）
```

上表与「`args[2]` 此前未使用」这一点都写进 `docs/design/injection-points.md`：
`args[2]` 从"未使用"变成"有定义"，属于**协议文档变化**而不是格式变化
（chunk/记录布局没动，见 ADR 0005）。

### 2. 建图规则：三个信号，缺一不建边

一条 `call` 边 `caller → callee` 需要：

1. 一条转移码为 `1`（call）的 `RegWrite`，`args[1]` 是目标地址（callee）；
2. 该事件的 `address` 字段是**发起调用的那条指令**（caller 侧）；
3. 目标地址是**代码**：它必须在本轨迹里作为某条事件的 `address` 出现过
   （自洽性检查 —— 返回地址/跳转目标必然会被执行到，否则我们凭什么说它是代码）。

`ret` 边用转移码 `2` 同理，方向是"从当前函数返回到目标地址"。

**任何一条不满足就不建边**，并把原因计数报出来（`未采纳：目标不是代码 N 条`）。
宁可少画边，不可画错边：**一张漂亮但错的调用图会把后续所有推理带偏**，
而少一条边的代价只是"这里没看清"。

### 3. 与"栈事件"的关系

原始需求提到"`reg_write` + 栈事件"。这里**没有**要求栈事件，理由是：

- `INS_IsCall`/`INS_IsRet` 已经直接给出了"这是一次调用/返回"这一事实，
  不需要再从"栈指针变化 + 栈上写入一个代码地址"去**推断**它；
- 推断版本会把"跳转 + 手工改栈"误判成调用（第 2 条背景），
  而调用图里一条错的边会**级联**出错的调用者/被调用者关系。

栈事件仍然有用（以后判断帧大小、参数位置），但不作为建边的必要条件。

### 4. 诚实边界

- 探针**默认关**（`-pb_transfers 0`），与其他探针一致：默认零成本。
  没有探针数据时，建图结果就是"0 条边"，且报告必须**明说原因**
  （"这份轨迹里没有转移事件"），而不是报一个看起来正常的空图。
- 间接调用（`call rax`）的 `IARG_BRANCH_TARGET_ADDR` 是**运行期**目标，
  探针能覆盖；但目标落在**未插装模块**（如系统 DLL）时，图里会出现
  指向"我们没插装过的地址"的边 —— 这类边会以 `外部目标` 计数报出，
  而不是混进正常边里。
- 折叠（`Repeat`）会吞掉中间的转移事件 ⇒ 折叠过的轨迹建图**会缺边**。
  所以建图前必须展开，且结果里带上"输入是否展开/是否有折叠"的说明。

## 代价

- 每个 `call`/`ret` 一次回调（相对"每条内存访问"量级小得多）；
- 事件量增加：一次调用 1 条（返回 1 条）。对 100 万次调用的目标约 200 万条事件 ⇒
  必须配合既有的**前置过滤**与**折叠**（这也是为什么折叠与它的关系要写清）。

## 备选方案（以及为什么不选）

| 方案 | 为什么没选 |
|------|-----------|
| 只从 `mem_write`（栈上返回地址）推断 | 跳转/异常展开/手工改栈都会产生同样形状 ⇒ 假边 |
| 用 `BreakpointHit` 反推调用关系 | 断点是我们自己下的 ⇒ 只能看到"我们关心的点"，还原不出主要调用关系 |
| 每指令插装，记录所有寄存器变化 | 事件量爆炸（每指令 1+ 条），且本 ADR 只需要调用/返回 |
| 新增事件 kind 表示调用/返回 | 格式 v1 已冻结；`RegWrite` 的未用 arg 槽足够表达，不必动格式 |

## 验证

- `crates/pinbridge-trace/src/callgraph.rs` 的用例：完整 call/ret 建边；
  **缺转移码不建边**；**目标不是代码不建边**；`ret` 方向正确；
  自环不建边；空输入报"没有转移事件"而不是"空图"。
- 端到端：`pin_tool_transfers`（ctest）—— 打开探针跑靶子，要求
  `转移事件：call N / ret M`（N、M 非零），并 `pinbridge calls` 出一张非空的图。
