# 0005. 轨迹用自定义二进制格式（`.pbt`）

- 状态：已采纳
- 日期：2026-10-16
- 相关：[../specs/pbt-format.md](../specs/pbt-format.md)、[../design/trace-compression.md](../design/trace-compression.md)

## 背景

插装带来的事件量级远超原生执行。对抗场景下的实测特征：

* VMP 外壳会把关键循环展开成"同一条指令 + 同地址 + 同参数"重复几万到几亿次；
* 一条 5 分钟会话按原样录制可以达到**几十 GB**；
* 这些数据里 99.99% 是同一个字节序列，但**不能直接扔掉**——
  重复次数本身就是信息（"这段解密循环跑了 4 万次"）。

同时轨迹必须是**可复现的证据**：读回来要能还原出原始事件序列，
并且要被两个独立实现（Rust 与 Python）读懂。

## 决策

自定义二进制格式 `.pbt` v1，三条设计：

1. **chunk 序列容器**（而不是"一个 section 一个长度"）：
   录制线程必须能边跑边写，而定长 section 头要求提前知道总长度；
2. **记录级 delta + varint + zigzag**：地址与参数相对上一条记录做差，
   小数值 1 字节；
3. **重复折叠标记**（`EVENT_REPEAT`）：段首原样保留、段尾写
   `{sequence=段内最后一条, args[0]=折叠条数, args[1]=原始类型}`，
   展开是**逐字节可逆**的。

跨语言一致性用**黄金字节**保证：同一组记录 → 同一条字节流 → 两侧测试共同断言。

## 考虑过的替代方案

| 方案 | 为什么没选 |
|------|-----------|
| JSON Lines | 字段名开销在亿级记录上是纯浪费（`"address":` 11 字节 × 每次）；体积不可接受 |
| Protocol Buffers / FlatBuffers | 引入依赖与代码生成；且无法表达"折叠标记"这种语义（它是格式级的语义，不是 schema 级的） |
| MessagePack / CBOR | 同样引入依赖；压缩率不如 delta + varint |
| 直接存 zstd 压缩的文本 | 压缩后**部分损坏会毁掉整段**（不可定位）；而且"证据可读"对分析很重要 |
| 复用现成的 trace 格式（perf/ETW/Chrome trace） | 语义不匹配（我们需要四种介入时机的类型、序号单调性、折叠语义） |
| SQLite | 单文件、可查询，但写入放大严重（插装热路径不能等 fsync）；且引入依赖 |

## 后果

**得到**：

* 体积可控（VMP 场景下折叠率常见 0.99+，再叠加 delta）；
* 可流式写入与读取，内存占用与"记录数"成正比而非"事件数"；
* 损坏可定位（chunk 边界、记录边界都很明确）；
* 两个独立实现 + 黄金字节 → 跨语言不会静默分叉。

**付出**：

* 格式是我们自己的 → 必须自己写规范、自己维护向后兼容
  （`FORMAT_VERSION` 与读侧的"拒绝未知类型"策略）；
* 调试不如文本直观 → 用 `pinbridge replay` / `pb-replay` 提供可读输出作为补偿；
* 读侧的防御必须做全（chunk 长度上限、varint 上限、`argc` 越界、
  未知类型、截断）——轨迹文件是**不可信输入**。

## 已知的边界

* 折叠统计在**落盘侧**做；Hub 的窗口查询是在切片上折叠的，
  跨窗口边界的折叠计数不完整（文档里写明了）；
* 不支持"边录边查历史"（要查完整历史必须等 `finish` 或读已落盘部分）；
* `FORMAT_VERSION` 变化时，旧版本**会明确拒绝**而不是尽力解析——
  这条是刻意的（见 [../specs/pbt-format.md §8](../specs/pbt-format.md)）。
