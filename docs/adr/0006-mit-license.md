# 0006. 采用 MIT 许可

- 状态：已采纳
- 日期：2026-10-16
- 相关：[`LICENSE`](../../LICENSE)、[`third_party/pin/README.md`](../../third_party/pin/README.md)

## 背景

PinBridge 的定位是**安全研究工具**：它要被研究员在真实对抗里用起来、
要被集成到各种 agent 工作流里、要被别人拿去改造。

同时它依赖 Intel Pin（闭源、按 Intel 自己的许可分发，不入库）。

## 决策

* 本仓库的代码：**MIT**；
* Intel Pin：不包含、不重新分发，由使用者按 Intel 的条款自行获取
  （`third_party/pin/` 在 `.gitignore` 中排除）；
* 不使用 GPL/AGPL 类许可：那会让"集成进别人的工具链"变成法律问题，
  与工具的目标冲突。

## 考虑过的替代方案

| 方案 | 为什么没选 |
|------|-----------|
| Apache-2.0 | 同样合适，且带专利授权条款；但 MIT 更短、更少措辞争议，对本项目足够 |
| MIT OR Apache-2.0 双许可 | Rust 生态的常见选择，但对"一个工具项目 + 中文团队"来说维护两套声明没有实际收益 |
| GPL-3.0 | 会阻止闭源集成；研究工具的价值在于被广泛使用 |
| AGPL-3.0 | 同上，且对"本地工具"没有实际约束意义 |
| 完全不声明许可 | 默认保留全部权利，等于不允许任何人使用——与目标相反 |
| 自定义"仅供研究"许可 | 许可条款的模糊性本身就是风险；而且我们已经在文档层面写清了使用边界 |

## 后果

**得到**：

* 任何人都可以自由使用、修改、集成、二次分发；
* 与 Pin 的许可解耦（我们不分发 Pin，只分发使用说明）；
* 依赖审计简单（`deny.toml` 的允许列表以 MIT/Apache-2.0/BSD 为主）。

**付出与边界**：

* MIT 不提供专利授权（若将来出现专利风险，可再评估换 Apache-2.0）；
* 许可**不能**约束使用行为 → 使用边界写在
  [README](../../README.md)、[SECURITY.md](../../SECURITY.md)、
  [CODE_OF_CONDUCT.md](../../CODE_OF_CONDUCT.md) 里：
  **只对拥有或已获授权的目标使用**；
* 贡献者的代码默认按 MIT 发布（在 [CONTRIBUTING.md](../../CONTRIBUTING.md) 里说明）。
