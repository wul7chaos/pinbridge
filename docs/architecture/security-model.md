# 安全模型与威胁边界

PinBridge 会**主动修改另一个进程**、会让**AI 自主决策**、会**解析外部文件**。
这三件事各自带来一类风险，本文件把它们摊开讲清楚。

## 信任边界图

```text
        ┌────────────────────── 受信任（本机、同一用户）─────────────────────┐
        │  AI 客户端 ──stdio──▶ pinbridge-mcp ──▶ HubService                │
        │                                        │                           │
        │                          回环 TCP（拒绝非 127.0.0.0/8）             │
        │                                        ▼                           │
        │                       agent（在目标进程内）                        │
        └───────────────────────────────────────────────────────────────────┘
                                          │ 插装
        ┌─────────────────────────────────▼─────────────────────────────────┐
        │  半信任：被分析的目标进程                                          │
        │  * 可能检测/干扰我们（功能范畴，不是漏洞）                          │
        │  * 可能崩溃（会带走 agent，所以轨迹必须流式落盘）                    │
        └───────────────────────────────────────────────────────────────────┘

        不可信输入：.pbt 轨迹文件、agent 上报的原始字段、样本本身
```

## 威胁 1：目标程序的对抗

**这是什么**：目标主动检测调试器/插装、检测时序、故意设陷阱（TF 单步陷阱、
异常洪泛）、自校验内存与代码。

**态度**：这是**功能问题**，不是漏洞。目标做得对，我们做得不够。

**对策**：

* 基座选插装而不是调试器框架（不依赖被分析进程的异常路径）；
* 不假设"目标会乖乖执行"——所有 hook 都必须能承受目标在异常里打转；
* TF 虚拟化（[../design/flags-virtualization.md](../design/flags-virtualization.md)）
  避免"物理 TF 生效在代码缓存里"这类暴露；
* 事件采集走有界通道，目标即使进入指令级死循环也不会把我们拖崩。

**怎么报告**：开普通 issue，标签 `对抗`，用"对抗场景记录"模板。

## 威胁 2：AI 主体越权

**这是什么**：执行者是自主主体。它会试错、会重试、会探索边界。
人类不会在 60 秒里尝试 200 次越权操作，AI 会。

**态度**：**这是漏洞**。任何让 AI 拿到未授予能力的路径都必须修。

**对策（四层）**：

| 层 | 机制 | 失效时的后果 |
|----|------|--------------|
| 1 | 默认最小能力（AI = `mem_read` + `trace_record`） | — |
| 2 | 会话 ceiling 约束一切授权 | 授权被限制在人类预设范围内 |
| 3 | epoch 让在途命令失效 | 人类接管后 AI 无法继续写入 |
| 4 | 双端能力校验（Hub + agent） | 单端绕过不成立 |
| 5 | 全程溯源 | 事后能定位是谁做的、用哪版脚本 |

**明确的已知限制**：M0 阶段 Hub 与 agent 之间的链路是**本机回环 TCP，未加密、
未认证**。同一台机器上的另一个进程理论上可以连上端口伪装成 Hub。
这在 M1 的待办里（选项：命名管道 + 对端进程校验，或 `SO_PEERCRED` 类机制）。
在此之前，请不要在多用户机器上运行 agent。

## 威胁 3：轨迹文件作为不可信输入

**这是什么**：`.pbt` 可能来自同事、CI、issue 附件，甚至对手。
它是二进制、有长度字段、有变长整数——典型的"能被构造输入打崩"的格式。

**对策**（都在代码里有对应测试）：

| 攻击面 | 防御 |
|--------|------|
| 声称巨大长度的 chunk | 单 chunk 上限 256 MiB，超过即报错 |
| 超长 varint（无限推进） | 超过 10 字节判定为损坏 |
| 未知事件类型 | 拒绝，**不猜默认值** |
| `argc` 越界 | 超过 8 即报错 |
| 自相矛盾的折叠标记 | 严格模式拒绝（默认）；取证场景必须用严格模式 |
| 截断文件 | 明确报"在哪条记录之后被截断" |
| 数据类型 0（保留值） | 拒绝（Python 侧同样拒绝） |

**一条原则**：宁可失败，也不要"尽力而为地解析出一堆看似合理的数据"。
在安全分析里，**错误的完整结论比明确的失败昂贵得多**。

## 威胁 4：供应链

**对策**：

* 依赖面极小（M0：`serde` / `serde_json` / `thiserror` / `sha2`，全部是生态标准件）；
* `Cargo.lock` 入库，CI 用锁定版本；
* `cargo deny` 在 CI 检查许可证、公告、依赖来源；
* `deny.toml` **显式禁止** `reqwest` / `ureq` / `openssl-sys` / `tokio`：
  一个"能下传代码的调试工具"是我们不愿制造的东西，也不愿给它一个网络栈；
* `unsafe_code = "deny"` 在 workspace 级默认开启，只有 `sys` 与 `agent` 显式放行，
  且每块 `unsafe` 必须写成立前提。

## 威胁 5：我们自己犯错

这是最现实的一类。对策：

* 丢数据必须计数并上报（否则"我看到的"会冒充"发生过的"）；
* 未实现必须显式报错（否则 AI 会在错误前提上继续推理）；
* 跨语言两个实现 + 黄金字节用例（否则两侧静默分叉）；
* C ABI 用 `static_assert` 把布局钉在编译期；
* 端到端自检 `pinbridge demo` 进 CI（否则"骨架早就断了但没人发现"）。

## 明确不做的事

| 不做 | 理由 |
|------|------|
| 远程控制面 | agent 链路只允许回环；把调试能力开给网络是不可接受的默认 |
| 自更新 / 代码下传 | 调试工具的"自助升级"等于给它一个永不失效的入口 |
| 内置样本 / 授权材料 | `.gitignore` 里对 `samples/` 是硬禁止；文档里也不写获取方式 |
| 绕过授权或许可 | 这是分析工具，不是攻击工具 |
| 静默降级 | 唯一例外是列在 `docs/roadmap.md` 里的桩函数，它们会**显式**报 `not_supported` |

## 使用者责任

请只对**你拥有或已获授权**的目标使用 PinBridge。
维护者不会协助、也不会讨论对未授权目标的分析。
